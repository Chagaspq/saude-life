# Falas do vídeo de apresentação (Saúde Life)

Vídeo: `apresentacao/video-apresentacao.mp4` (1920×1080, 15:53 minutos, sem áudio), nas 8 partes do roteiro.

Tempo de fala de cada um: Gabriel Chagas 04:37 · Rafael 03:38 · Tomas de Oliveira 04:13 · Hiago Tetsuo 03:24

Antes de gravar a voz, troquem **[curso]**, **[instituição]** e **[contatos do grupo]** pelas informações de vocês (aparecem na primeira e na última tela e na fala de abertura).

## Como gravar

1. Cada um grava **o rosto e a voz** lendo as próprias falas (pode ser no celular, de frente, com boa luz).
2. No editor (CapCut, Clipchamp, Premiere...), coloque o vídeo da tela por baixo e o **vídeo do rosto** de quem está falando no **quadrado tracejado** à direita:
   **posição x = 1472, y = 32, tamanho 416 × 416** (num vídeo 1920 × 1080). A cor do tracejado mostra de quem é a vez.
3. A legenda embaixo mostra a fala na hora certa, então dá para ler enquanto grava.
4. Se a fala ficar mais longa ou mais curta, é só congelar ou acelerar a imagem um pouco no editor.

### Parte 3 · Front-end

**06:09 a 06:31 · Rafael (PH) Santos (15) · Tecnologias e pastas**  
Agora o front-end. Ele foi feito em React, com HTML, CSS e JavaScript, usando o Vite para rodar e gerar o site. O código fica na pasta src: em páginas, uma tela por arquivo; em componentes, as peças reaproveitadas; em lib, os serviços que conversam com a API; e em estilos, o CSS.

**06:31 a 06:53 · Rafael (PH) Santos (15) · O que é um componente**  
Um componente React é uma função que devolve um pedaço da tela e pode ser reaproveitado. Este é o CartaoNumero: ele recebe o rótulo, o valor, o detalhe e o ícone, e monta o cartão. A mesma peça aparece no Início, na Evolução, no resumo do treino e no painel do administrador.

**06:53 a 07:08 · Rafael (PH) Santos (15) · Componente em uso**  
Aqui ele sendo usado no Início. Basta chamar o componente com textos diferentes: meta da semana, sequência, treinos realizados e tempo treinado. Se mudarmos o visual do cartão em um lugar, muda em todas as telas.

**07:08 a 07:31 · Rafael (PH) Santos (15) · Controle das telas**  
Cada tela tem o próprio endereço, e o controle de quem pode abrir cada uma fica no componente AppLayout. Sem login, a pessoa vai para a tela de entrar. Quem ainda não respondeu o questionário vai para ele. E o cliente não abre o painel do administrador, nem o administrador abre as telas do cliente.

**07:31 a 07:51 · Rafael (PH) Santos (15) · Conversando com a API**  
Para falar com o servidor, todas as telas usam a função api. Ela monta a requisição com o método, o endereço e os dados em JSON, envia o token do login no cabeçalho e, se der erro, devolve a mensagem que a API mandou para mostrar na tela.

**07:51 a 08:09 · Rafael (PH) Santos (15) · CSS e responsividade**  
O CSS organiza o layout. As cores e os espaços ficam em variáveis, e as media queries mudam a tela conforme a largura: abaixo de novecentos pixels aparece o menu embaixo, como num aplicativo de celular, e os cartões passam para duas colunas.

**08:09 a 08:22 · Rafael (PH) Santos (15) · No celular**  
E aqui o mesmo Início no tamanho de um celular. A tela se reorganiza sozinha: os cartões ficam um embaixo do outro e o menu de baixo dá acesso às cinco abas.


### Parte 4 · Back-end

**08:22 a 08:42 · Tomas de Oliveira (17) · Tecnologia e pastas**  
No back-end usamos Java com Spring Boot. A API fica na pasta backend e é dividida assim: modelo, com as tabelas como classes; repositório, que faz os comandos no banco; controle, com as rotas; dto, com o formato dos dados; e segurança, que cuida do login.

**08:42 a 09:02 · Tomas de Oliveira (17) · Rotas principais**  
A API recebe as requisições do site, aplica as regras e conversa com o banco. Estas são as rotas principais: GET para buscar, POST para criar, PATCH e PUT para alterar e DELETE para apagar. As rotas do administrador começam com barra admin e só abrem para ele.

**09:02 a 09:20 · Tomas de Oliveira (17) · Código de uma rota**  
Este é o código de uma rota: o POST de refeições. O Spring recebe o JSON, confere os dados, monta a refeição com o dono, o dia e as calorias, salva no banco com o repositório e ainda dá os pontos da refeição.

**09:20 a 09:42 · Tomas de Oliveira (17) · Regras e validações**  
As validações ficam nos pedidos: o nome é obrigatório, a senha precisa ter pelo menos oito caracteres e o e-mail precisa ser válido. Nos pontos, a mesma ação nunca conta duas vezes e o limite é de trezentos por dia. Se algo estiver errado, a API devolve o erro com uma frase em português.

**09:42 a 10:00 · Tomas de Oliveira (17) · Conexão com o SQL Server**  
A conexão com o SQL Server fica neste arquivo de configuração: o endereço do servidor, a porta mil quatrocentos e trinta e três, o nome do banco, o usuário e a senha. O driver da Microsoft está no arquivo pom ponto xml.

**10:00 a 10:19 · Tomas de Oliveira (17) · Autenticação**  
Sobre a autenticação: a senha é guardada só como um resumo BCrypt. No login, a API gera um token, e o site manda esse token em toda chamada. Este interceptador confere o token antes de cada rota, e as rotas de administrador só abrem para administrador.

**10:19 a 10:31 · Tomas de Oliveira (17) · Testando: login**  
Testando no estilo do Postman: um POST no login com e-mail e senha. A resposta tem o código duzentos, o token e os dados do usuário, sem a senha.

**10:31 a 10:46 · Tomas de Oliveira (17) · Testando: buscar treinos**  
Agora um GET nos treinos, mandando o token. A API devolve em JSON as fichas da pessoa, com os exercícios, as séries, as repetições e a carga, e também o treino que o administrador mandou.

**10:46 a 10:57 · Tomas de Oliveira (17) · Testando: erro**  
E quando algo dá errado: o login com a senha errada devolve o código quatrocentos e um, com a mensagem pronta para aparecer na tela.


### Parte 5 · Banco de dados

**10:57 a 11:13 · Hiago Tetsuo (10) · SQL Server**  
Agora o banco de dados. Usamos o Microsoft SQL Server, o banco relacional que estudamos no curso. Ele garante as chaves primárias e estrangeiras e os relacionamentos, e o Management Studio facilita ver e consultar os dados.

**11:13 a 11:31 · Hiago Tetsuo (10) · Modelo entidade-relacionamento**  
Este é o modelo entidade-relacionamento, com doze tabelas. A academia tem vários usuários. O usuário tem várias fichas de treino, e cada ficha tem vários exercícios. O usuário também tem vários treinos concluídos, refeições, pesos e pontos, e a academia tem vários avisos.

**11:31 a 11:49 · Hiago Tetsuo (10) · Script de criação**  
Este é o script de criação. Na tabela de usuários, o id é a chave primária, o e-mail é único, o tipo só aceita cliente ou administrador, e academia id é a chave estrangeira que aponta para a tabela de academias.

**11:49 a 11:58 · Hiago Tetsuo (10) · SELECT**  
Um SELECT simples nas contas. Repare na coluna senha hash: a senha nunca fica guardada como texto, só o resumo criptográfico.

**11:58 a 12:10 · Hiago Tetsuo (10) · JOIN com GROUP BY**  
Agora um JOIN com GROUP BY: para cada cliente, a academia, quantos treinos fez e quando foi o último. É exatamente o que aparece no painel do administrador.

**12:10 a 12:23 · Hiago Tetsuo (10) · JOIN de três tabelas**  
Este JOIN junta três tabelas: o usuário, a ficha de treino e os exercícios, em ordem. Aqui aparece o treino que o administrador mandou agora há pouco na demonstração.

**12:23 a 12:37 · Hiago Tetsuo (10) · INSERT**  
Um INSERT: publicamos um aviso direto pelo banco para a academia de demonstração. Logo depois, o SELECT mostra que ele foi gravado, junto com o aviso que o administrador publicou pelo site.

**12:37 a 12:47 · Hiago Tetsuo (10) · UPDATE**  
E um UPDATE: mudamos a meta semanal do cliente de demonstração para cinco treinos por semana, e o SELECT confirma a mudança.

**12:47 a 13:04 · Hiago Tetsuo (10) · View e índices**  
Criamos também uma view, que é uma consulta salva com o resumo de cada cliente: treinos feitos, último peso e pontos. E temos índices nas tabelas de treinos, refeições e pesos, que deixam rápidas as buscas por pessoa e por data.


### Parte 6 · Fluxo completo

**13:04 a 13:21 · Rafael (PH) Santos (15) · 1. O usuário clica**  
Para mostrar tudo funcionando junto, vamos registrar uma refeição. Na tela de Alimentação, o usuário clica em adicionar refeição, preenche o jantar com quinhentas e cinquenta calorias e clica em salvar.

**13:21 a 13:35 · Rafael (PH) Santos (15) · 2. O front envia**  
Quando a refeição é salva, o front-end chama a API: esta função envia um POST para a rota de refeições com o nome, o horário e as calorias, levando o token do login.

**13:35 a 13:48 · Rafael (PH) Santos (15) · 3. A API valida e grava**  
Na API, a rota de refeições recebe o pedido, valida os dados com o arroba Valid e executa o save, que vira um comando INSERT no SQL Server.

**13:48 a 13:58 · Rafael (PH) Santos (15) · 4. O SQL Server grava**  
No banco, o SELECT mostra o jantar que acabou de ser gravado, com as calorias, a proteína e a data de hoje.

**13:58 a 14:15 · Rafael (PH) Santos (15) · 5. A tela atualiza**  
A API devolve o código duzentos e um com o id do banco, e a tela é atualizada: o jantar aparece na lista e as calorias e a proteína são somadas nas barras do dia. Tela, API e banco funcionando juntos.
